# 函数模块源码格式规范化设计

## 1. 背景与现场证据

2026-08-13 在 SAP DEV 客户端 `300`、开发包 `Z001`、传输 `S4HK900011` 上执行了 `ZMCP_IF_TEST + Z_MCP_IF_TEST` 组合创建验证。

真实流程已经成功完成以下阶段：

- 创建函数组和函数模块。
- 写入包含 `IMPORTING`、`EXPORTING` 与实现代码的完整 `source/main`。
- 写后语法检查、解锁和 Eclipse 同构激活。
- 读取 active 函数模块源码。

失败发生在最后的源码复核。计划源码 SHA-256 为 `3dc6defb90b773122a378acb75f84adf858b72e45295deb21eb941a198a53bfc`，SAP active 源码 SHA-256 为 `61fffc1b5ccd32b32f18124078bcf1a5d3ec60bfed89816d66f03013e0733536`。对现场哈希反推后确认，SAP 只做了两类格式化：

1. 将换行改为 `CRLF`。
2. 将函数签名终止句点与首条实现语句之间补为三个空行。

参数、缩进、注释和业务语句没有证据表明发生变化。现有比较器只允许换行符与文件末尾换行变化，因此把该结果判定为 `DIFFERENT`，随后安全工作流成功反向删除函数模块和函数组，计划终态为 `COMPENSATED`。SAP 搜索已确认两个测试对象均无残留。

## 2. 目标

- 允许 SAP 对函数模块签名后分隔空行做确定、受限的格式规范化。
- 保持参数声明、实现代码、注释、缩进和正文空行的严格比较。
- 保留原始目标哈希、实际哈希和明确的匹配类型，确保审计可解释。
- 同时覆盖函数模块创建后的验证、已有函数模块修改后的验证及其回滚验证。
- 不改变 `PROGRAM`、`INCLUDE`、`CLASS` 或其他对象的比较规则。

## 3. 不在范围内

- 不忽略任意空白、缩进、大小写或注释差异。
- 不修改发送给 SAP 的源码，也不提前猜测并插入 SAP 格式。
- 不增加结构化函数参数生成器。
- 不改变激活、锁、传输、补偿或用户确认协议。
- 不自动重试真实 SAP 写入。

## 4. 方案比较

### 方案 A：函数模块专用受限规范化（采用）

在通用比较器之外增加函数模块专用比较入口。它先执行现有严格比较，仅在仍不匹配时，对完整函数模块源码中“签名终止句点之后、首条非空正文之前”的连续空行做规范化，再比较全文。

优点是影响范围最小，能够解释现场差异，同时不会放宽正文安全边界。

### 方案 B：提交前按 SAP 格式改写源码

调用方或工作流预先补齐三个空行。该方案依赖单一 SAP 版本的当前表现，仍可能因其他格式化规则产生误判，并污染用户确认的原始源码，因此不采用。

### 方案 C：忽略全部空白差异

该方案会掩盖字符串、注释、缩进和正文结构变化，无法满足源码完整性验证要求，因此拒绝。

## 5. 比较模型

### 5.1 通用比较保持不变

`compareSources` 继续只产生：

- `EXACT`
- `LINE_ENDING_NORMALIZED`
- `DIFFERENT`

现有对象和调用方行为不变。

### 5.2 新增函数模块比较

新增独立的函数模块比较函数，按以下顺序判断：

1. 原始哈希相同：返回 `EXACT`。
2. 仅换行符或文件末尾换行不同：返回 `LINE_ENDING_NORMALIZED`。
3. 两份源码都能识别为完整的 `FUNCTION ... ENDFUNCTION.` 框架，且只在签名终止句点后的连续空行数量上不同：返回 `FUNCTION_MODULE_FORMAT_NORMALIZED`。
4. 其他任何差异：返回 `DIFFERENT`。

函数签名终点定义为从 `FUNCTION` 声明开始，第一条以句点结束的语句。规范化只移除该终点之后、下一条非空行之前的连续空行。正文内部、`ENDFUNCTION.` 之前以及文件其他位置的空行不做处理。

若任一源码不能安全识别完整函数模块框架，函数模块专用规范化必须失败关闭并返回 `DIFFERENT`。

## 6. 工作流接入

- `AbapObjectCreationWorkflow`：仅当创建对象为 `FUNCTION_MODULE` 时使用函数模块专用比较器；父函数组仍只验证 active 状态。
- `AbapChangeWorkflow`：函数模块激活后验证和函数模块回滚后验证使用同一专用比较器。
- 其他对象继续调用现有 `compareSources`。
- 原始 `expectedHash` 与 `actualHash` 不做规范化，继续反映 SAP 实际返回内容。
- 计划状态、审计事件和状态查询记录新的 `sourceMatchType`，便于区分普通换行规范化与函数模块格式规范化。

## 7. 错误与恢复

- `FUNCTION_MODULE_FORMAT_NORMALIZED` 视为验证成功，流程继续进入 `APPLIED`。
- 参数、正文、注释、缩进或非签名分隔区空行变化仍返回 `DIFFERENT`，沿用现有回滚或创建补偿。
- 激活结果未知、复读失败或对象状态无法证明时，继续禁止自动重试和不安全删除。
- 本次设计不改变 `COMPENSATED`、`COMPENSATION_FAILED`、`ROLLED_BACK` 等终态语义。

## 8. 测试设计

### 8.1 比较器单元测试

- 完全一致返回 `EXACT`。
- 仅 CRLF 和末尾换行变化返回 `LINE_ENDING_NORMALIZED`。
- 现场源码与 SAP 三空行格式返回 `FUNCTION_MODULE_FORMAT_NORMALIZED`。
- 无参数的 `FUNCTION name.` 同样支持签名后空行规范化。
- 参数名称、类型、方向或实现语句变化返回 `DIFFERENT`。
- 注释、缩进、正文内部空行或 `ENDFUNCTION.` 前空行变化返回 `DIFFERENT`。
- 不完整或无法识别的函数模块源码返回 `DIFFERENT`。

### 8.2 工作流测试

- 组合创建在 SAP 补签名后空行时进入 `APPLIED`，不触发补偿。
- 已有函数模块修改在相同格式化下进入 `APPLIED`。
- 函数模块回滚验证接受相同格式化。
- `PROGRAM` 的任意中间空行变化仍触发失败与恢复。

## 9. 验证与验收

实现后先运行定向测试、全量 Jest、TypeScript 构建和 `git diff --check`。随后重新构建并重启 MCP，再使用同一测试对象与传输执行一次新的真实 SAP DEV 组合创建。

真实验收标准：

- 创建计划终态为 `APPLIED`。
- 函数模块完成创建、写入、语法检查、解锁、激活和复读。
- 函数组与函数模块均验证为 active。
- 函数模块 `sourceMatchType` 为 `FUNCTION_MODULE_FORMAT_NORMALIZED`。
- 不执行补偿。
- `inspectAbapObject` 能读取包含参数和实现代码的 active 源码。
- Eclipse 中对象与传输内容一致。

若真实请求超时、连接中断或返回未知激活结果，停止验证并先做只读状态检查，不重复调用应用。
